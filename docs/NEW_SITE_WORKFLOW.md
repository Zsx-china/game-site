# 新游戏站标准流程

适用于从 `game-site-template` 建立或换皮游戏站。开始前必须取得：游戏名、域名、建站资料目录；首发语言未明确时，以建站资料为准，不从模板猜测。

按“第零部分资料采集 → 六部分站点实现”的顺序执行，并按下方模式取得确认。项目资料是事实来源；模板只提供结构，不提供新游戏的事实。

## 执行模式

### 标准模式

默认使用标准模式。完成当前部分的验收、汇报实际结果并得到用户确认后，才能进入下一部分。

### 快速首发模式

用户提出“抢排名”“一个上午上线”或明确要求快速首发时启用。目标是在资料和外部服务正常时，用约 4–5 小时发布可索引的英文 MVP；不承诺固定上线时间或搜索排名。

1. 只设三道确认门：
   - **启动门**：确认游戏、域名、上线语言、关键词 JSON 中的分类和首发文章数；该确认同时授权首发范围内的文章生成。
   - **发布前门**：汇报首页、关键事实和实际完成的文章数；确认后执行最终生产验收。
   - **上线门**：汇报验收结果，并取得明确的 GitHub 推送和 Vercel 部署授权。
2. 两道门之间连续执行；发现资料实质冲突、来源或文章缺失、提供商或模型不可用、构建或验收失败时立即停止并汇报。
3. 未指定首发文章数时，从项目规划和关键词 JSON 中选择 8–12 个最高意图页面；分类仍只以关键词 JSON 为准。其余文章后续增量发布，不承诺一个上午从零完成 30–40 篇。
4. 第零部分边界不变：搜索和采集期间只能准备独立目录、素材清单、资料到配置的映射和部署前提；第零部分验收通过后才能修改站点业务文件。
5. 采集仍使用远端 SEOScout 与青果代理；生成仍在本地按 `docs/SEOSCOUT_GENERATION_WORKFLOW.md` 执行。用户选择的提供商和模型必须先通过当前 `/models` 查询及真实提示词预检；保留成功文件，只补缺失项。
6. 快速模式不得省略文章 metadata、占位符、格式和明显事实支撑检查，也不得省略旧品牌与中性占位扫描、分类同步、生产 `site:check`、sitemap、站内链接、未知路由 404、桌面与移动端检查。部署获批后还要检查 HTTPS 和代表性生产页面。
7. 目标时间预算：启动与准备约 30 分钟，资料采集约 60 分钟，首批 8–12 篇生成与检查约 90 分钟，站点配置与导入约 90 分钟，验收与部署约 60 分钟。模型、代理、YouTube、DNS 或证书异常会延长时间；排名还取决于索引、内容质量、域名和竞争度。

## 资料名称映射

- 用户提到的 `基础信息.md`、`languages.json`、`favicon_io/`、关键词文件或首页模块等名称，可以是功能性称呼或占位名称，不要求实际文件同名。
- 先查看用户指定的建站资料目录，再按用途选择实际存在的等价资料。用户明确指定的文件优先，其次是与项目同名的主资料文档。
- 不因占位名称不存在而停止，也不从旧模板补猜缺失事实。例如 Enfosi 的 `基础信息.md` 实际对应 `Enfosi建站资料.md`。
- 同一用途存在多个候选、内容冲突或用途无法判断时，再向用户确认最终来源。

## 第零部分：SEOScout 资料采集

第零部分通过验收并向用户汇报前，只能准备独立项目目录，不修改模板或站点业务文件。

1. 在本地运行 `python tools/seoscout_preflight.py <关键词 JSON> --project <项目名>`；以输出的项目名、分类数和关键词数作为后续计数基准，不手工估算。
2. 在 VPS `/root/seoscout` 做运行前检查：私密 `.env` 存在，只检查青果代理相关键是否存在而不输出值；确认 `.venv/bin/seoscout` 和 `.venv/bin/yt-dlp` 可执行；将 `.venv/bin` 加入 `PATH`；启用 `USE_PROXY_FOR_EXTRACT=true`；每个新站使用独立项目名和输出目录。
3. 先运行 `seoscout search --keywords <关键词文件>`。确认 `output/<项目>/out/search_results.json` 存在、可解析，且搜索关键词数等于预检数量，再记录网页和 YouTube 的实际结果数及失败项。
4. 搜索验收通过后才运行 `seoscout collect --project <项目名> --keywords <关键词文件>`。断点续采保留已有结果，只补缺失来源；退出码 0 不代表采集完整。
5. 递归检查 `output/<项目>/out/collected/**/*.json`：文件总数和各分类数量、零字节、JSON 解析、缺失/重复/意外关键词、每个关键词的有效来源，以及网页和 YouTube 的成功/失败数。确认没有同项目残留进程。
6. 将操作错误与来源限制分开汇报。`RequestBlocked` / `IpBlocked` 使用新代理连接重试；`TranscriptsDisabled` / `NoTranscriptFound` 或重试后仍被封锁时记录并跳过，永不下载音频或语音转写。

验收：预检关键词数 = 搜索关键词数 = 采集文件数；分类数量一致；文件均非空且可解析；每个关键词至少有一个有效来源；实际来源数、失败原因和残留进程数已汇报。标准模式停止并等待确认；快速首发模式在第零部分验收通过后按三道确认门继续。

## 第一部分：基础配置

1. 从建站资料确认游戏名、域名、主题色、官方游戏与开发者链接、Hero 图片、视频来源和 favicon。
2. 先按“旧品牌快速门禁”扫描复制后的模板；零命中直接使用，只有发现残留时才清理对应旧内容。更新站点配置、公开站点 URL、品牌名与简称，将 `Game Site Template`、`GS`、`example.com` 等中性占位值替换为当前项目资料；空官方链接和视频 ID 按资料配置，缺少来源时保持隐藏。
3. 只按资料更新要求的主题变量，不顺带重做整套配色。
4. 替换 favicon、PWA 图标、Hero 和视频预览图；验证文件非空、真实格式和尺寸。社区视频必须标为社区内容，不得写成官方预告。
5. 更新 manifest，并确保页面引用它。Header、Hero、视频替代文本必须使用正确游戏名。
6. 保持 Hero 后紧接视频区域；复用模板现有组件和配置，不创建重复常量或组件。

验收：资源格式和尺寸正确；站点配置、manifest 和可见首屏无旧品牌；locale JSON 可解析；lint、build 通过；桌面和移动端各做一次页面检查。

## 第二部分：SEO 与法律页

1. 更新页面 metadata、canonical、Open Graph、Twitter Card、robots、sitemap 和结构化数据中的站点品牌、域名、图片与 logo。
2. 更新隐私政策、服务条款、版权和关于页面；删除旧游戏、旧平台、旧开发商和旧域名声明，避免虚构官方关系。
3. Hero CTA 分别指向官方游戏、入门内容和文章列表；最终 CTA 使用当前游戏和平台事实。
4. Footer 外链及标签必须与实际来源一致；没有官方 YouTube 或 Discord 时，不得把社区链接标为官方。
5. 保留用户明确排除的首页模块，不借本部分扩大改写范围。

验收：公开 URL 为无扩展名规范路径；canonical、sitemap、robots 同域；JSON-LD 可解析且 logo 存在；法律页和本部分修改区域无旧品牌；locale 校验、lint、build 通过。

## 第三部分：多语言与导航

1. 先从建站资料确定当前上线语言；条件性未来语言不提前启用。英语首发时只保留 `en`。
2. 同步 `src/i18n/routing.ts`、`src/i18n/request.ts`、`src/locales/*.json`、语言切换器和 `content/<locale>/`，不得只改其中一处。
3. 删除未启用语言的 locale 文件。新语言尚无翻译时使用空 JSON，不复制英文冒充翻译。
4. 先检查导航和内容类型；中性模板已为空时直接通过，发现旧游戏分类时才清理对应配置及硬编码入口。保留菜单、主题切换等框架文案，避免界面显示翻译键。
5. 先检查 `content/**/*.mdx`；仅删除确认属于旧游戏的文章，零篇时不重复清理，当前项目文章保持原样。保留 `content/` 和当前上线语言目录，用 `.gitkeep` 保证空目录可进入 Git。
6. 语言或内容为空导致组件类型失败时，只做恢复同步所需的最小修改。

验收：上线语言在配置、导入、locale 文件、切换器和内容目录中完全一致；旧 MDX 数量为零；旧导航为空（当前项目已确认导航保留）；locale 校验、lint、build 通过。空内容引起的动态导入警告可以记录，但构建失败不能忽略。

## 第四部分：首页模块

1. 从建站资料和首页模块资料建立旧字段到新文案的对照，再按模板现有 schema 更新；只改本部分明确列出的首页模块。
2. 入门卡片围绕玩家前两小时的需求，保持纯展示时不添加链接；游戏介绍、统计和 FAQ 只使用资料中可核验的事实。
3. 首页 SEO 模块的数量、顺序、名称、描述、链接、展示类型和 highlights 以项目资料为准；保留模板已有渲染分支，不为换文案新增组件。
4. 模块名称包含当前游戏名；卡片标签使用简短英文文本，不使用 emoji，不添加无资料支撑的机制、数值或代码。
5. 广义的“删除内部链接”指删除旧站或无关链接；schema 明确要求的站内导航 `href` 必须保留并指向实际分类路由。

验收：首页模块数量和必填字段与资料一致；链接指向当前站点真实路由；目标模块无旧品牌、占位符和无关链接；locale JSON 可解析，locale 校验、lint、build 通过。

### 模板交互效果

- Hero 鼠标光晕由 `SITE_CONFIG.home.pointerGlow` 控制，默认开启；仅在支持悬停的精细指针设备上显示，触屏和减少动态效果设置下关闭，装饰层不得阻挡点击。
- 公共 `.ui-button` 按住时缩放至 98% 并轻微变暗；禁用按钮不触发该反馈，减少动态效果时取消缩放。沿用公共按钮，不扩展为全站卡片、文字的按压动画。
- 文章详情页自带顶部 2px 阅读进度条，按正文可阅读范围计算；正文开始、半程和末尾对应约 0%、50% 和 100%，短正文隐藏，首页和分类页不显示。当前没有独立配置开关，不新增无需求的配置项。
- 验收：核对桌面及 375px 布局、深浅主题、真实按住与释放、触屏和减少动态效果；确认光晕不挡点击、按钮释放恢复、正文进度正确且无横向溢出。运行 `node scripts/check-pointer-glow.mjs`、`node scripts/check-reading-progress.mjs`、`npm run lint` 和生产构建；空模板的测试文章放在独立验收副本，不导入生产内容。

## 第五部分：文章与导航

1. 只有生成文章目录存在且非空时才导入；缺失时如实汇报，禁止创建假文章。只导入当前上线语言，生成和翻译仍属于另行确认的 SEOScout 流程。
2. 以项目关键词 JSON 的分类字段作为唯一分类真相源，不从模板、文章标题或目录猜分类。
3. 同步分类键和顺序到导航配置、locale 导航文案、顶层分类概览、内容分组标题与排序、分类列表页和 sitemap；框架菜单与主题切换文案可以保留。
4. Header 从导航配置生成；侧边栏动态扫描 MDX 并按分类顺序排列；Recent Updates 按 `lastModified || date` 倒序。
5. 每个内容类型提供 `overviewTitle` 和 `overviewDescription`；首页模块入口必须改到实际分类路由。
6. 保留成功文章并只补缺失项。导入后逐文件核对来源与目标路径、数量、分类分布、metadata 分类；可用哈希确认原样复制。导入完成即运行目标站 `npm run site:check`，提前拦截明确 MDX 占位 token；第六部分按此后的实际变更范围选择复核级别。token 规则以模板 README/脚本为唯一事实源。

### 内页版式基线

模板已按参考站（enfosi.online）的内页正文版式落地，新站直接沿用，不要逐站另调：

- 正文列 `max-w-[864px]`（`src/app/[locale]/[...slug]/page.tsx` 的 `#article-reading-body` 与 `src/components/article-body.tsx` 的 `article-prose`）；页头标题区仍保持 `max-w-[760px]`，相关文章区块同为 `max-w-[864px]`（与正文列对齐）。正文文本靠 `article-prose` 的 `pr-8` 收到 832px 宽（与参考站一致），容器仍为 864px，将来加广告轨时偏移量不变。
- 正文排版 `text-lg leading-8 text-foreground`（18px / 行高 32px、近黑墨色），段落不再加 `max-w-[72ch]` 限制；表格单元格、步骤列表、清单同理改用 `text-foreground`，`peer-checked` 变体保留。
- 桌面目录改为正文上方的内联卡片：导语与元信息之后、`MobileTOC` 之后渲染 `<SidebarTOC headings={item.headings} label={messages.shared.tableOfContents} currentPathname={…} />`，外层 `mt-8 hidden lg:block`；不再使用浮动右侧目录（`article-toc.tsx` 已从模板删除）。

不要动：模板内没有任何广告组件，广告轨位偏移（`calc(50%±…)`）属于已挂广告的站点，与本节无关；手机端、首页模块和分类列表页版式不在本节范围；文章长度与生成规格保持原样。

验收：构建通过；正文容器 864px、正文文本 832px、字体 18px/行高 32px、文字为 foreground 墨色；1440 与 1280 宽度下 `scrollWidth === clientWidth`；`lg` 及以上能看到内联目录卡片，页面里没有浮动目录。

### 文章增强：快速指南与内嵌视频

每次新站导入文章时执行本节；组件沿用模板，内容按当前项目资料逐篇选择，不要求每篇都有模块。生成阶段按 `docs/SEOSCOUT_GENERATION_WORKFLOW.md` 准备内容，导入后再核对实际渲染。

- **快速指南**：入门、操作、Boss、解谜等有明确行动要点的文章，优先在文件开头的 `export const metadata` 中添加可选 `quickGuide: string[]`，一般 3–5 条短句，只总结正文及可靠来源已经支持的结论；`**关键词**` 可加粗。缺少可靠要点时省略字段，不用标题列表凑数。模块由文章页渲染在导语及元信息后、MDX 正文前，不在正文重复写，也不进入目录。空数组或缺失时隐藏；超过五条会提示文件路径并只显示五条，编辑时应主动精简。
- **内嵌视频**：参考站采用随正文内容插入的方式：将 `<VideoEmbed youtubeId="实际11位ID" title="准确的视频标题" />` 放在正文中与视频相关的小节内，在必要的说明、步骤或要点之后展示，不固定放在文章开头或第一个 H2 之前。按内容关联选择位置，不按固定屏数或段落数插入；示意文字必须替换后才能保存为文章。视频须与文章主题直接相关，默认一个；没有合适来源就省略，不批量给所有文章插片。用户指定其他位置时按其要求调整，首页视频仍单独配置。
- **视频来源**：从本项目采集结果或可核验页面选择，核对游戏、内容、作者、可嵌入状态及与正文的关联；官方与社区来源如需说明，写在相邻正文中并如实标注。不得沿用模板预览的视频 ID，不虚构视频，不下载音频或转写；没有合适来源就省略。`youtubeId` 只填 ID，`title` 必填且使用当前文章语言，不手填内部 `videoIndex`，不添加重复组件或手写 iframe。
- **播放配置**：核对 `src/config/site.ts` 的 `SITE_CONFIG.videoAutoplay`，模板默认 `true`；需要关闭时设为 `false`。开启时只有文章第一段视频带静音自动播放和 iOS 内联参数，其余视频使用普通嵌入；每段视频达到约 30% 可见后才挂载，离开视口后保留。实际自动播放受浏览器策略限制；首页视频配置与文章内嵌视频分别核对。
- **模板来源**：复制前按“模板基线”确认实际版本包含 QuickGuide 与 VideoEmbed。若能力仅在本地未提交或未推送改动中，明确记录差异和来源，不把旧远端版本当作已具备，也不自行提交或推送。

本节验收：记录带快速指南及视频的文章路径、数量、视频来源和自动播放配置；无合适内容的文章允许为零。快速指南核对条目与正文一致、最多五条、加粗有效、无空列表项，缺失字段时无残留框；视频核对插入位置、不进入目录、延迟加载且滚出不卸载。使用目标站已有的 `test:video`、`scripts/check-quick-guide.mjs`（存在时）及 `npm run site:check`，抽查代表文章的深浅主题、桌面和 375px 布局；确认无横向溢出、标题和 iframe 属性正确。不为凑验收向生产内容加入测试文章。

验收：实际文章总数和各分类数量与关键词 JSON 一致；来源与目标文件一致；导航、locale、分组顺序、列表页和 sitemap 分类完全同步；metadata 完整且分类等于父目录；运行文件旧品牌扫描为零；locale 校验、lint、build 通过。

## 第六部分：上线前验收

先对照第五部分验收通过后的变更文件，再选择以下一种路径。无法确认变更是否影响运行时时，执行完整核验。项目提供 `npm run site:check` 时优先运行该命令；脚本结果仍须按生成的 JSON 报告和实际服务进程核验。

### 轻量复核

仅当以下条件全部满足时使用：第五部分的 `npm run site:check` 已通过；此后只修改文档、验收脚本或其他明确不进入构建产物的文件；页面、文章、导航、路由、SEO、locale、静态资源、构建和部署配置均未改变。

1. 核对第五部分后的实际 diff，记录为何不影响运行时。
2. 再运行一次 `npm run site:check`，核对报告、失败项及服务进程是否清理。
3. 若检查失败或发现运行时文件变化，立即转为完整核验。

### 完整核验

第五部分后修改了页面、文章、首页模块、导航、路由、SEO、locale、静态资源、构建或部署配置中的任一项时执行。

1. 完成路由和内容后执行生产构建，再用生产模式启动当前工作区；未确认部署目标时只做本地验收，不擅自提交、推送或部署。
2. 解析 sitemap 并访问其中每个 URL，核对 URL 总数、唯一性、重定向和 HTTP 状态；构建成功不能替代实际访问结果。
3. 从已访问页面提取同站内部链接并逐一检查，包括 sitemap 未收录的 Header、Footer、CTA 和正文链接。
4. 同时检查每页 H1、Loading 占位和运行文件旧品牌残留；`site:check` 必须基于生产页面核对 TOC/页内 fragment 的目标 id、每页 canonical 与 sitemap URL 严格一致、canonical/hreflang 均为同域绝对 HTTPS URL，且根 URL 保留唯一尾斜杠、其他路径不带尾斜杠。开发模式中的偶发错误必须用生产构建复核后再判断根因。
5. 修复后重新检查失败 URL 和完整 sitemap，确认无 404/500、重复 URL 或失效内部链接，并停止本地服务。逐项人工核对 `next.config` 远程图片域名：已无运行时引用的旧域名必须删除；静态扫描不能可靠证明动态拼接域名是否仍在使用，不为此编写猜测性门禁。

完整验收：生产模式构建通过；sitemap 非空且所有 URL 唯一并返回 200；站内链接无失效；页面 H1、Loading 占位和旧品牌检查通过；汇报实际 URL 数、失败数、修复项和未执行的部署动作。

### 获得部署授权后

部署不重复完整本地验收。默认只确认部署任务成功、首页返回 200，并各抽查一个分类页和文章页；仅当线上结果与本地不一致时扩大检查范围。没有分类页或文章页时，改查两个代表性公开页面。

## 旧品牌快速门禁

1. 验收时只扫描实际运行文件（如 `src/`、`public/`、`content/`、站点配置和 locale），排除 `node_modules/`、`.next/`、`.git/`、`graphify-out/` 等依赖、构建和历史目录。
2. 每个新站首次复制模板及各部分验收时都执行扫描。零命中直接通过，不重复清理已中性化模板；只有命中旧游戏名、域名、开发商、平台或视频 ID 时，才检查并修复对应运行文件及引用。清理后重新扫描，保留当前项目内容和可复用框架。
3. 生成或历史目录中的旧内容单独标记为归档残留，不得误报为网站运行时残留，也不得未经用户确认删除已跟踪的历史或缓存文件。
4. 汇报时明确区分“运行文件残留数”和“归档残留数”。
5. 中性模板占位配置是待填写项，不是游戏事实：每个新站仍须核对 config、locale、法律页、manifest、图标、图片、导航与 CTA。上线前单独扫描 `Game Site Template`、`example.com`、占位说明、空必填配置及无关外链，确认均已按项目资料替换或有明确保留理由；模板本地检查通过不能替代新站验收。

## 安全边界

- 不删除或覆盖未确认来源的用户文件和未提交改动。
- 不根据旧模板、聊天记录或目录名猜游戏事实。
- 不把退出码 0 当作完成；按文件、数量、路径、内容和构建结果验收。
- 标准模式的文章生成、翻译和部署须另行确认；快速首发模式只在启动门授权的文章范围内生成，翻译仍须另行确认，GitHub 推送和部署必须在上线门明确授权。
- 旧聊天记录只作历史备份，不作为新站流程或事实来源。
